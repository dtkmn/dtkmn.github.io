The fastest way to misunderstand MCP is to watch a demo and think you have seen the system.

The agent discovers a tool. The schema looks clean. The call succeeds. The response lands in the chat. Everyone nods because the protocol did what the protocol promised.

That is useful.

It is also nowhere near production.

MCP solves a real integration problem. I argued that in [MCP: The USB-C of AI Integrations](/posts/mcp-the-usb-c-of-ai-integrations/): without a common protocol, every AI surface and every external tool becomes another custom integration. MCP turns bespoke wiring into a repeatable contract.

But a contract is not an operating model.

Production MCP starts after the happy path works. It starts when the server has an owner, the tool has a policy boundary, the deployment can be repeated, the logs can answer an incident question, and dependency alerts do not sit there like unexploded debt.

If that makes the topic feel less exciting, good. That is where the engineering is.

## The protocol boundary is necessary

MCP gives AI systems a shared way to discover capabilities and call tools. A host runs the AI experience. A client speaks MCP. A server exposes tools, resources, and prompts.

That boundary matters because it stops the model from freehanding access to your systems. The model does not "just call the scanner" or "just query production." It sees a declared capability with a name, description, and schema. The client routes the request. The server executes code you own.

That is the right shape.

It is not the whole boundary.

MCP does not decide who should be allowed to scan a target. It does not know whether the target belongs to you. It does not know whether a destructive option needs human approval. It does not know which team owns the server when a queue backs up at 2 a.m. It does not make a dangerous action safe because the arguments were valid JSON.

MCP gives the system grammar. Production decides where judgement lives.

## The missing layer is operational

Most MCP demos optimize for the visible magic.

The model asks for something. The tool runs. The output appears.

That proves the protocol path. It does not prove the server belongs near real systems.

A production review has to ask harder questions:

- Who owns this server?
- Who can discover it?
- Who can connect to it?
- Who can call each tool?
- Which tools require approval?
- Which arguments are constrained by policy?
- Which targets are explicitly allowed or rejected?
- Which inputs, outputs, errors, and decisions are logged?
- Can an operator replay what happened?
- Can the server be deployed the same way twice?
- Can it be rolled back or killed quickly?
- Does it fail closed when identity, policy, or downstream services fail?

If the answer is "we can add that later," you are not building production MCP. You are building a demo with a liability backlog.

That sounds blunt because it should. Agents turn integration mistakes into action mistakes. Once a model can invoke tools, the risk is no longer a bad answer in a chat window. The system can query data, trigger workflows, run scans, mutate state, open tickets, send messages, or produce artifacts that other humans trust.

That changes the standard.

## Operator-visible security is the product

Security controls are weaker when only the platform team can see them.

In production, the responsible operator needs to understand what the system will allow, what it blocked, and why. That does not mean every end user needs a security console. It means the people carrying the risk need inspectable controls.

For MCP, that usually means four layers.

First, identity. The system needs to know who is asking, whether that is a human user, a service, or an automated workflow.

Second, server-level access. Not every host should be able to connect to every MCP server. A general chat surface and a privileged security workflow should not inherit the same reach just because they both speak MCP.

Third, tool-level authorization. Being allowed to connect to a server is not the same as being allowed to invoke every tool on it. A low-risk documentation lookup and a high-risk scan, deploy, or production query do not belong behind the same permission check.

Fourth, argument-level and action-level policy. Valid JSON is not valid intent. The server still needs to validate target URLs, environment names, query scopes, destructive flags, rate limits, workspace quotas, cost limits, and approval requirements.

That is why the more serious production-MCP examples are interesting. The important part is not that a company used MCP. It is that MCP sits inside a broader operating model: registry, ownership, auth, authorization, deployment paths, observability, and incident response.

The boring controls are not paperwork. They are the product.

## Deployment reality decides whether the design survives

There is a reason production systems converge on paved roads.

If every team has to invent its own MCP deployment story, most teams will choose one of two bad options. They will avoid building servers because the platform work is too heavy, or they will build snowflake servers that pass demos and fail operations.

The many-small-servers model is attractive because it keeps domains coherent. A data warehouse server can have different controls from a documentation server. A security scanning server can have different limits from a ticketing server. The model's tool context stays smaller, and the blast radius stays more legible.

But many small servers only work if the deployment burden is low.

Production MCP needs repeatable packaging, configuration, auth integration, logs, metrics, ownership metadata, health checks, versioning, rollout mechanics, and rollback paths. It needs a registry that is more than a directory. The registry has to become a control plane for discovery, approval, status, support ownership, and policy.

Otherwise, "many small servers" becomes "many small operational messes."

This is where builders often lie to themselves. They say they are building an ecosystem when they are accumulating integration demos. An ecosystem has distribution, governance, upgrade paths, documentation, and failure handling. A pile of clever servers is not an ecosystem.

It is a pile.

## Live maintenance pressure is part of the proof

Production proof is not a frozen screenshot of a working demo. It is the system continuing to make defensible changes after reality hits it.

That is the useful lesson from the June maintenance trail on [MCP ZAP Server](/projects/mcp-zap-server/). The v0.9.0 release on June 10 did not just add more tools. It moved policy, audit, and abuse-protection handling toward shared gateway-core adapter boundaries; added reusable GitHub Actions and GitLab security-gate examples; tightened CI image-reference validation; and updated dependency surfaces including Spring AI, Netty, and the docs stack.

The v0.9.1 release on June 26 is the more important maintenance signal because it refuses to freeze the proof at the exciting part. It bumps runtime, Helm, MCP Registry, and install metadata to `0.9.1`; refreshes gateway-core to `0.5.10`; moves Spring Boot to `4.0.7`, Spring AI to `2.0.0`, Gradle to `9.6.0`, and the docs stack to Astro `7.0.3`; and archives old release notes under `docs/releases/` instead of leaving root-level snapshots to rot.

The security-alert context matters because it removes the fantasy that production readiness means nothing ever fires. GitHub dependency alerts on June 10 flagged high-severity Netty issues. The branch moved to Netty `4.2.15.Final`, and GitHub marked the relevant Dependabot alerts fixed the same morning. On June 26, the release overrode Spring Boot's Jackson 2 BOM to `2.22.0` so the runtime no longer resolved `jackson-databind` `2.21.4`; hardened Snyk by requiring `SNYK_ORG`, checking for generated SARIF files, and bounding monitor steps; and updated support tables so `>= 0.9.1` is active while `0.9.0` is explicitly an upgrade target for dependency refresh.

That is not a blemish to hide. It is the point.

A real production-adjacent project has scanners, dependency submission, CI, release notes, and unresolved work that operators can see. A toy demo has a README and confidence. If you are exposing a security scanner through an agent protocol, the stronger proof is not "no alerts." The stronger proof is that alerts create visible remediation pressure and the project keeps moving under it.

Maintenance is not separate from the product. For production MCP, maintenance is evidence.

## MCP ZAP Server is the right kind of test

[MCP ZAP Server](/projects/mcp-zap-server/) is a better proof point than another toy integration because OWASP ZAP is not harmless.

The server lets agents import API schemas, run ZAP workflows, and return structured findings. That touches target ownership, network boundaries, scan intensity, authentication, false positives, report handling, operator trust, and evidence quality.

A weak demo stops at "the agent launched a scan."

A credible implementation has to answer harder questions:

- Can the server reject targets it should not scan?
- Can operators see which scan ran, who requested it, and why?
- Are scan limits explicit?
- Is authentication built in rather than hand-waved?
- Can tool scopes be constrained per client?
- Can policy be previewed, dry-run, and enforced?
- Can abuse protection shed load before ZAP is overwhelmed?
- Can the server run locally, in containers, and in Kubernetes without inventing a new deployment every time?
- Is the result structured enough for an agent to use without hiding the evidence?
- Can a security team inspect the project and understand the boundary?

The ZAP project is not interesting because MCP makes OWASP ZAP look shiny. It is interesting because it forces the production question early. Once an agent can drive a scanner, the protocol boundary has to meet security reality. You cannot pretend the tool call is the whole story.

That is exactly the mental model MCP needs.

## The checklist is not optional

If I were reviewing an MCP server for production, I would not start with the demo.

I would start with the operating contract.

What does the server expose?

Who owns it?

Who can discover it?

Who can connect to it?

Which tools are safe by default?

Which tools require approval?

Which arguments are constrained by policy?

Which logs prove what happened?

Which metrics show usage, errors, latency, cost, and value?

Which dependency and container scanners run?

Which alerts are open, fixed, dismissed, or awaiting upstream remediation?

Which failure modes fail closed?

Which deployment path is blessed?

Which version is running?

Who gets paged when it breaks?

That list is not glamorous. It is the price of letting agents operate near real systems.

The protocol makes the server easier to plug in. It does not make the server safe, useful, owned, observable, deployable, or maintained. Those qualities are earned separately.

## Where this leads

The next phase of MCP will not be won by the teams with the cleanest "hello world" demos.

It will be won by teams that make the boundary inspectable.

The AI surface should know which tools exist. The user should only see tools they can actually use. The operator should know who owns the server, what policy applies, how it is deployed, what happened during each invocation, what the current security posture looks like, and how to stop the system when something goes wrong.

That is the line between protocol enthusiasm and production engineering.

MCP matters because it turns integrations into contracts. But a contract is only useful when the organization can enforce and maintain it.

So yes, build the MCP server. Show the demo. Let the agent call the tool.

Then do the real work:

- make ownership explicit
- make authorization layered
- make dangerous actions confirmable
- make deployment boring
- make observability default
- make evidence replayable
- make dependency and scanner pressure visible
- make the boundary legible to the people carrying the risk

That is the standard.

Demos prove that the protocol can move.

Production proves that the system can be trusted after it starts moving.
