## What it is

This project turns OWASP ZAP into an MCP-accessible security tool so an AI agent can import API
schemas, run scanning workflows, and pull structured findings without falling back to brittle shell
scripts.

The reusable boundary layer now has its own site entry: [MCP Gateway Core](/projects/mcp-gateway-core/)
is the Java contract layer for tool identity, authorization, policy, audit, abuse protection, and
adapter behavior. This project stays responsible for the ZAP-specific runtime.

## Client Spider and browser authentication

**v0.13.0** adds **Client Spider**, ZAP's browser crawler for JavaScript-driven applications.
An agent can start a crawl immediately or submit it to the durable scan queue, with each crawl
independently tracked for status and cancellation. Guided workflows select it with `strategy=client`; the
existing `strategy=browser` still selects AJAX Spider.

Operator-managed browser login profiles also let Client Spider explore pages behind a login.
ZAP signs in through the browser and detects how the application carries its login session,
including cookies or tokens sent in request headers. This fixes a case where login succeeded in
Juice Shop's browser but the follow-up login check did not send the token and incorrectly reported
that authentication failed. These browser profiles currently support Client
Spider; the existing form-login profiles remain the path for guided authenticated active scans.

**Availability:** [v0.13.0 is published](https://github.com/dtkmn/mcp-zap-server/releases/tag/v0.13.0),
with AMD64 and ARM64 images on Docker Hub and GHCR. Upgrade all workers sharing a scan queue
before submitting Client Spider jobs. The
[Client Spider guide](https://danieltse.org/mcp-zap-server/scanning/client-spider/) covers setup,
required ZAP add-ons and Firefox, authentication, and both execution modes.

Anonymous and authenticated crawling were verified against Juice Shop in both direct and queued
modes. Crawl status confirms that the crawler has
stopped; meaningful coverage still needs evidence from discovered content and authenticated
requests. Findings feed the existing shared ZAP reports after passive analysis finishes. There is
currently no dedicated Client Spider discovery-list tool or report isolated to one crawl, and the
testing did not establish a coverage advantage over the other crawlers.

For a fresh ZAP session, the guide also documents a
[pre-login visit workaround](https://danieltse.org/mcp-zap-server/scanning/client-spider/#browser-storage-alerts-missing-during-login):
ask ZAP to visit the application's home page once before browser login. In the tested Juice Shop
setup, this allowed ZAP to save browser-storage alerts that were otherwise dropped during login.
It needs no full spider run and is not automatic in the guided workflow. The issue also reproduced
with v0.12.0 and ZAP alone, before any Client Spider crawl.

## Why it matters

Many MCP demos stop at convenience. This one is stronger because it sits on a real operational
boundary: security automation. The interesting question is not whether an agent can call a tool. It
is whether that tool can be exposed in a way that is safe enough, observable enough, and packaged
well enough to fit into actual engineering workflows.

## What makes it credible

The repository has enough surface area to show that it has moved past novelty:

- a documentation site with security, deployment, observability, and operator runbooks,
- a demo path that shows the workflow end to end,
- release notes and changelog discipline,
- GitHub Actions and GitLab security-gate examples,
- Docker Compose and Helm deployment material,
- API-key/JWT auth, tool scopes, runtime policy bundles, audit events, rate limits, workspace quotas,
  and target URL validation.

The June 10 v0.9.0 release made the proof sharper: policy, audit, and abuse-protection handling moved
through shared [MCP Gateway Core](/projects/mcp-gateway-core/) adapter boundaries instead of one-off
local filters. The security-gate examples rejected mutable image tags, and the release notes made
validation commands inspectable.

The July 16 v0.10.1 release is narrower than a feature launch and more useful as evidence. A
Streamable HTTP endpoint receives requests, notifications, and responses on the same `POST` route.
The previous gateway adapter treated a response-shaped envelope as a request, then rejected it for
having an `id` and `result` or `error` but no `method`. Cursor keepalive replies consequently failed
instead of reaching Spring AI for session correlation.

[PR #167](https://github.com/dtkmn/mcp-zap-server/pull/167) moved both gateway dependencies to
`0.7.2`. [PR #168](https://github.com/dtkmn/mcp-zap-server/pull/168) packaged that correction as
v0.10.1 and aligned runtime, OCI image, Helm chart, MCP Registry, extension-proof, and install
metadata. Response envelopes now pass through and complete with HTTP `202`; requests that carry a
`method` still take the existing authorization and abuse-protection path. The body, session id,
custom headers, body-size limit, and surrounding authentication chain remain intact.

This is a drop-in patch from v0.10.0, not an excuse to imply a larger redesign. Tool schemas,
authentication settings, Helm values, and the database contract are unchanged. The release also
expands CodeQL coverage and pins policy dry-run regression coverage, while the support table marks
`>= 0.10.1` active and `0.10.0` upgrade-only for this client-compatibility failure. That is what
production-adjacent maintenance looks like: a real downstream failure gets a bounded fix, a release,
and an explicit upgrade path.

That combination is exactly why this deserves a page here. The repository handles setup and usage.
This page explains why the project matters in the first place.
