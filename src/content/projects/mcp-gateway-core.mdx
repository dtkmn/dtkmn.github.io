## What it is

`mcp-gateway-core` is an embeddable Java governance contract library for MCP tool runtimes.
It gives downstream runtimes shared types and helpers for tool identity, access rules,
governance decisions, audit events, abuse-protection decisions, URL scope checks,
correlation IDs, and rate limiting.

It also publishes `mcp-gateway-spring-webflux`, an optional adapter that applies those contracts
to Spring WebFlux HTTP traffic.

That is the whole point. The project is not trying to be an MCP server SDK, Spring Boot starter,
OAuth provider, policy language, scanner layer, plugin system, proxy, or data plane. If it starts
swallowing those jobs, it becomes less useful.

## Why it exists

MCP servers keep running into the same governance questions:

- what tool is being called,
- which principal and workspace are attached to the call,
- whether the caller is authorized,
- whether a policy bundle allows or denies the request,
- how quotas, abuse protection, and rate limits are represented,
- what audit event survives after the tool call,
- which URL or target scope is allowed.

Those concepts should not be reinvented inside every MCP server. They also should not be tangled
with a specific product like OWASP ZAP, a specific auth provider, or a specific proxy runtime.

`mcp-gateway-core` exists to keep that middle layer boring and reusable.

## The boundary it enforces

The strongest design choice is the boundary, not the API surface.

The core artifact stays JDK-only. The Spring WebFlux adapter lives in a separate artifact. Storage,
scanner behavior, auth-provider wiring, observability backend, transport setup, and product-specific
tool behavior stay downstream.

The repository backs that up with build gates. The core build rejects scanner, runtime, private-repo,
and data-plane coupling. It checks JAR contents, Java 17 bytecode, `jdeps`, Maven Central bundle
shape, checksums, and signed dry-run payloads. The compatibility work compares public API against a
frozen `0.6.0` baseline and records accepted deltas for the public-preview line.

That is not glamorous. Good. This repo should be unglamorous. Its job is to stop each MCP server
from making up a different vocabulary for the same governance decisions.

## What the current evidence says

The honest status is public preview.

The `0.7.2` [core](https://repo1.maven.org/maven2/io/github/dtkmn/mcp-gateway-core/0.7.2/) and
[Spring WebFlux adapter](https://repo1.maven.org/maven2/io/github/dtkmn/mcp-gateway-spring-webflux/0.7.2/)
artifacts were published to Maven Central on July 16, 2026. This is a correctness patch, not an API
expansion: the release notes record no new public API or binary deltas.

The correction is specific. The WebFlux adapter now distinguishes response envelopes from requests
on the shared MCP `POST` endpoint. A pass-through response has no `method`, has a string or numeric
`id`, and has exactly one of `result` or `error`. A body carrying a `method` remains governed even if
it also contains response fields. Duplicate fields, case-variant governance fields, batches, and
ambiguous objects retain fail-closed handling.

Recognized responses skip request context, scope extraction, authorization, and action-based abuse
protection, then continue downstream for protocol validation and session correlation. The adapter
still preserves the body, session headers, configured body-size limit, and surrounding security
chain. That boundary matters: the gateway fixes its classification error without taking ownership
of full JSON-RPC validation.

[PR #41](https://github.com/dtkmn/mcp-gateway-core/pull/41) finalized `gatewayCoreVersion=0.7.2`
and updated the release notes and roadmap. It is release-preparation evidence, not publication
evidence; Maven Central is the actual receipt. The public trail is not perfectly synchronized: the
repository still labels the notes “Unreleased” and has no v0.7.2 GitHub Release entry. Pretending
otherwise would make this page cleaner and less accurate.

The security signal is also live, not cosmetic. On June 29, 2026, the
[Snyk workflow on `main`](https://github.com/dtkmn/mcp-gateway-core/actions/runs/28365344965)
failed after PR #24 merged. The run had Snyk configuration, scanned four Gradle projects, found
seven vulnerable paths in the Spring WebFlux adapter graph through `jackson-databind` `2.21.2`,
uploaded SARIF to GitHub Code Scanning, uploaded the SARIF artifact, and then failed on the enforced
Snyk exit code. On July 1, 2026, the
[same workflow passed on `main`](https://github.com/dtkmn/mcp-gateway-core/actions/runs/28506184319).

That is exactly the kind of maintenance pressure a boundary library should expose. A fake proof says
"security scanning exists." A better proof shows what happened when the scanner found something and
that the gate still existed afterward.

The publication/docs mismatch is part of the evidence too. For a contract library, stale release
state is a contract defect, even when the artifact itself is available and the runtime correction is
real. The useful claim is bounded: 0.7.2 is published, its adapter behavior is documented and
consumed by MCP ZAP Server, and the repository's post-publication release surface still needs cleanup.

## How it differs from MCP ZAP Server

[MCP ZAP Server](/projects/mcp-zap-server/) is a product-facing MCP server around OWASP ZAP. It has
to care about scan targets, ZAP execution, reports, findings, deployment paths, and operator safety
around a real security scanner.

`mcp-gateway-core` is lower and narrower. It does not know how to run ZAP. It does not store
findings. It does not decide what a scan means. It gives Java MCP runtimes a shared way to represent
tool governance decisions before and around the product-specific behavior.

That separation matters. If ZAP-specific concepts leak into the core library, the core stops being a
contract. If the ZAP server hand-rolls every governance decision locally, the server becomes harder
to inspect and harder to reuse. The useful architecture is a clean boundary: reusable governance
contracts in `mcp-gateway-core`, scanner behavior in MCP ZAP Server.

## How it connects to the writing

The production-MCP argument keeps coming back to the same uncomfortable point: a protocol is not an
operating model.

[Demos Are Cheap. Production MCP Is Expensive.](/posts/demos-are-cheap-production-mcp-is-expensive/)
uses live maintenance pressure as the test. `mcp-gateway-core` is the library-layer version of that
test: compatibility gates, docs/release sync, public-preview caveats, and a failed scanner workflow
that forces the next maintenance move.

[MCP: the USB-C of AI integrations](/posts/mcp-the-usb-c-of-ai-integrations/) explains why the
protocol matters. This project explains one thing the protocol does not give you automatically: a
reusable boundary for authorization, policy, audit, and abuse-protection decisions around tool calls.
