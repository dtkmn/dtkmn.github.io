## What it is

Loopwright is a small Python package and local web runtime for inspecting agent loops as evidence
systems. It routes context, retrieves evidence, drafts an answer, runs format and mechanical checks,
records verifier decisions, handles retries and refusals, and exposes a redacted public trace.

The important part is not the chat UI. The important part is the `LoopReport`: a typed artifact that
keeps the loop's decisions inspectable after the run has stopped.

## Why it matters

Agent-loop work is easy to fake. Add retrieval, add a retry, display a timeline, and the demo looks
responsible. That is not enough. A loop that cannot show what evidence it selected, why it retried,
what the verifier decided, and what got redacted is just prompt automation with a longer memory.

Loopwright is the practical counterpart to [Loop Engineering Needs a Flight Recorder](/posts/loop-engineering-needs-a-flight-recorder/).
The article sets the standard. This repo is where that standard becomes a runnable contract.

## What makes it credible

The project is credible because it keeps the product surface narrow:

- evidence routing across web snippets, indexed files, thread memory, and direct model knowledge,
- local Ollama first, with a generic OpenAI-compatible gateway path for deployment,
- explicit loop recipes, context providers, verifier metadata, retries, refusals, and public traces,
- durable thread state and public loop-run records in the local FastAPI app,
- local JSONL export for loop reports as the replay artifact boundary,
- dependency-free exports for OpenAI trace and LangGraph manifest shapes.

The July 6 evidence pass is not a victory lap. It says the project is alive and still has hard edges.
[Issue #55](https://github.com/dtkmn/loopwright/issues/55) tracks in-memory session state, `run_id`,
`session_id`, and local JSONL artifacts for replay/diff work. The useful signal is the correction in
that issue: a premature close was reversed until the replay/session patch is actually pushed,
CI-green, and merged. That is the right posture. Do not let the roadmap lie for the sake of polish.

[Issue #56](https://github.com/dtkmn/loopwright/issues/56) keeps framework interop in its place. The
repo can export toward OpenAI trace tools, LangGraph manifests, and a future Microsoft Agent
Framework mapping, but those frameworks do not get to define the core product before the internal
report shape is stable.

The dependency-maintenance queue is also visible. On July 6, 2026, Dependabot opened
[PR #76](https://github.com/dtkmn/loopwright/pull/76) for `pypdf` `6.14.2`,
[PR #77](https://github.com/dtkmn/loopwright/pull/77) for FastAPI `0.139.0`, and
[PR #78](https://github.com/dtkmn/loopwright/pull/78) for Uvicorn `0.50.0`. Each one touches both
`pyproject.toml` and `requirements.txt`. That is not glamorous, but it is exactly the maintenance
pressure a local AI runtime has to absorb.

## What it is not

Loopwright is not a planner, scheduler, tool-use framework, or multi-agent runtime. Those are later
layers. The current job is simpler and harder to fake: make one loop's evidence, checks, verifier
state, retry/refusal behavior, and public trace inspectable.

If that layer is weak, adding autonomy only makes the failure harder to diagnose.

## How it connects to the writing

[Loop Engineering Needs a Flight Recorder](/posts/loop-engineering-needs-a-flight-recorder/) is the
principle. Loopwright is the package that should be judged against it.

[Why Local LLMs Matter in 2025](/posts/why-local-llms-matter-in-2025/) explains why private runtime
boundaries still matter. [Simulate Customer Outcomes Before Shipping AI Agents](/posts/simulate-customer-outcomes-before-shipping-ai-agents/)
explains why loop evidence has to survive contact with user-facing workflows. Loopwright sits between
those arguments: private/local enough to inspect, structured enough to review, and deliberately
unfinished where replay and framework interop still need harder proof.
